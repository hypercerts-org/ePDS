Optional secure-hardware key protection: accounts can have their data-signing key held in a locked-down secure enclave, and every user can get a built-in crypto wallet that only they can authorize — the server operator can never read, use, or trap the keys, and users can always recover or leave with their wallet.

**Affects:** End users, Client app developers, Operators

**End users:** nothing changes in how you sign up or sign in. On instances that enable the wallet, your account can create crypto wallet addresses (Ethereum-compatible and Solana) — no seed phrase to manage, and only requests approved on your device can spend from it. Your wallet's secret is split three ways (your device, the secure server hardware, and a recovery backup you control): the server alone can never spend or block your funds, you can recover the wallet if you lose your device, and you can always take your keys and leave.

**Client app developers:** six new wallet operations on the PDS when the operator sets `EPDS_WALLET_ENABLED=1`, all fully separate from ATProto repo reads/writes. Each is available both as a REST route (`/wallet/*`, shown below) and as an XRPC method under the `app.gainforest.wallet.*` Lexicon namespace (`/xrpc/app.gainforest.wallet.enroll`, `.create`, `.getWallet` (query ≡ `GET /wallet/info`), `.sign`, `.export`, `.recover`) with identical bodies and responses. Wallet keys follow a Privy-style 2-of-3 Shamir share model (server share in the enclave, device share + recovery share held by the user):

- `POST /wallet/enroll` (OAuth/access token required) — register the user's request public key: body `{ "requestPublicKeyHex": "<compressed P-256, 66 hex chars>" }`. First key wins (trust-on-first-use); re-enrolling a different key returns `409` (rotation happens via recovery).
- `POST /wallet/create` (OAuth/access token required) — generates the wallet inside the enclave (per-wallet entropy → BIP-39 → EVM `m/44'/60'/0'/0/0` + Solana `m/44'/501'/0'/0'`) and returns `{ wallet, deviceShareJwe, recoveryShareJwe }`. The share JWEs are encrypted to the enrolled request key — decrypt the device share locally and keep it, and re-protect the recovery share under a user-controlled recovery factor (password / user cloud). `409` if the wallet already exists.
- `GET /wallet/info` (OAuth/access token required) — returns `{ did, enrolled, wallet: { evm: { address, publicKeyHex }, sol: { address, publicKeyHex }, version, createdAt } | null, walletEncryptionPublicJwk }`. Use `walletEncryptionPublicJwk` (also on the signer's `/v1/attestation`) to encrypt shares sent to the enclave.
- `POST /wallet/sign` — body `{ "payload": "<base64url JSON>", "sig": "<base64url compact P-256 signature over SHA-256(payload)>" }`. The payload carries `did`, `purpose` (`wallet/evm` with a 32-byte `digestHex`, or `wallet/sol` with `messageBase64`), `deviceShareJwe` (the device share, JWE ECDH-ES/A256GCM-encrypted to `walletEncryptionPublicJwk`), a strictly increasing `nonce`, and an `iat` within a freshness window (default 120 s). No PDS token is required or accepted as authorization here — the user-signed envelope is the authorization, and without a genuine share the enclave cannot even reconstruct the key. Bad envelopes/shares return `403`, replayed nonces `409`.
- `POST /wallet/export` — same envelope shape with `op: "export"` (no `purpose`/digest). Returns `{ exportJwe }` — the mnemonic, entropy, and per-chain private keys encrypted to the enrolled request key. Credible exit: the PDS relays ciphertext it cannot read.
- `POST /wallet/recover` (OAuth/access token for transport) — body `{ "recoveryShareJwe": "<recovery share encrypted to the enclave>", "requestPublicKeyHex"?: "<new device key>" }`. Real authorization is possession of a share that reconstructs this wallet. Re-shards with fresh coefficients (old shares — including one on a stolen device — become useless), optionally rotates the enrolled request key, and returns fresh `deviceShareJwe` + `recoveryShareJwe`.

**Operators:** all off by default; with no new env vars set, behaviour is unchanged.

- New workspace package `packages/signer` — a standalone signing service that holds a root seed, derives per-user repo signing keys, and manages per-wallet 2-of-3 Shamir shares (server shares stored AES-256-GCM-encrypted under a root-seed-derived KEK; device/recovery shares only ever leave as JWEs encrypted to the user). In production it must run on confidential-compute hardware (dstack in a TDX/SEV-SNP confidential VM — never Railway/plain Docker); `pnpm dev:signer` runs it locally. Configure via `SIGNER_PORT`, `SIGNER_DATA_DIR`, `SIGNER_INTERNAL_SECRET`, `SIGNER_ROOT_SEED_HEX`/`SIGNER_ROOT_SEED_FILE`, `SIGNER_ALLOW_DEV_SEED`, `SIGNER_WALLET_FRESHNESS_SEC`, `SIGNER_DSTACK_SOCK`. The signer's sqlite store must be backed up/replicated — it holds each wallet's (encrypted) server share, but never enough shares to spend.
- New pds-core env vars: `EPDS_SIGNER_URL` (master switch), `EPDS_SIGNER_SECRET` (must match `SIGNER_INTERNAL_SECRET`; startup fails with "EPDS_SIGNER_SECRET must be set when EPDS_SIGNER_URL is set" if missing), `EPDS_SIGNER_REQUIRE_ATTESTATION=1` (refuse unattested signers — set in any real deployment), `EPDS_TEE_REPO_SIGNING=1` (enclave-signed repo commits for adopted accounts + `POST /_internal/tee/adopt` migration endpoint), `EPDS_TEE_ADOPT_ON_SIGNUP=1`, `EPDS_WALLET_ENABLED=1`.
- See `docs/design/tee-signer.md` for the architecture, threat model, and migration/rollback procedure before enabling repo signing.
